## Goal

Implement the surplus formula as pure arithmetic over value objects.

```
surplus = income
        − fixedCommitments                  (taken as-is, NEVER capped)
        − Σ min(actual, effectiveBaseline)  (CAP_AT_BASELINE categories only)
        − Σ userLineItems                   (the user's own named commitments)
        − discretionaryFloor
```

## The baseline is a default, not a rule

The local baseline is only ever the **fallback**. Where the user has stated their own figure, that
figure is what the formula uses — they know what they actually spend on entertainment, and a
government average does not.

```
effectiveBaseline = the user's own figure, if they set one
                  = localBaseline,          otherwise
```

**Do not implement that choice here.** It is already resolver layer 1 in `costofliving`, where
`USER_PROVIDED` beats even `OFFICIAL`, permanently. You consume a `CategoryObservation` that already
carries the resolved figure, and you never ask where it came from. Asking would drag provenance into
the arithmetic, and the moment the math can see confidence someone writes
`if (confidence == ESTIMATED)` inside the calculation.

## User-defined line items are first-class inputs

The user can create their own named commitments — "football stadium tickets, $300 a month" — and they
must count in the surplus rather than sitting in a note somewhere.

```
UserLineItem(id, label, SpendCategory parent, Money monthlyAmount, Rigidity rigidity)
```

- **The parent category decides how it enters the formula**, so a custom item needs no new formula
  arm. A $300 match ticket parented to `ENTERTAINMENT` is discretionary; one parented to
  `SUBSCRIPTIONS` is taken as-is. Adding a user item must never require touching
  `SurplusCalculation`.
- **Rigidity comes along from the start** — `DISPOSABLE`, `FLEXIBLE`, `ESSENTIAL`, `LOCKED` —
  defaulted from the parent category and overridable per item. P7 acts on it; you carry it faithfully.
  Carrying it now is what stops P7 having to widen the contract later.
- **Items are named in the output**, so downstream advice can say *"cut your match tickets by $50"*
  rather than *"cut Entertainment by $50"*.

`SurplusBreakdown` therefore reports per-line-item detail, not only per-category totals.

## Constraints that are the whole point

- **Pure.** No Spring, no I/O, no clock — the evaluation date arrives as a parameter, exactly as
  `AllocationRequest.asOf` does. `ArchitectureTest` enforces this and will fail the build. It is why
  these tests run in milliseconds.
- **One switch, over `BaselinePolicy`, three arms.** Never switch on `SpendCategory`. Adding a
  category must stay a one-row change.
- **Fixed commitments are never capped.** A cost-of-living index says what things *cost*, not what
  you *should spend*. Capping rent at the baseline pretends the user can underpay their lease and
  overstates the surplus. This bug nearly shipped;
  `rentAboveTheLocalBaselineIsStillSubtractedInFull` exists to catch its return.
- **Negative surplus is a real answer.** Do not clamp to zero — that hides overspend and makes the
  tradeoff engine understate the cuts needed.
- **`TRANSFER_INTERNAL` is never subtracted.** It aggregates into `alreadySaving`, which is displayed
  ("you already save $400/mo") and flows into the surplus.
- **The discretionary floor arrives as a `Money` and is subtracted whole.** You do not compute it —
  deriving it from the user's lifestyle tier and obligation load belongs to P4. Use realistic literals
  in tests, and **never zero**: a zero floor is what makes the engine recommend cutting all
  entertainment to nothing.

## One change outside your package

Add `Money residualGap` to `AllocationResult`, non-zero when suggested cuts still cannot close the
gap. Today the user sees three cuts and reasonably assumes the goal is now reachable. **Make this your
first commit**, so P7 can branch after it.
