## What Hasan asked for

> When someone enters everything and the app makes a plan, the first thing it should show is how much
> money is being left over — for saving, or just not spent — **from the data they entered, not after
> shifting it.** First show the original, then show tips on how to improve it.

## Why the current screen gets this wrong

The dashboard opens on **"Each month for your goals"**, which is `surplus.amount`. That figure is
already *shifted*: it charges capped categories at the local baseline instead of what the user spends,
and charges all going-out spending at the floor instead of what they actually spend. With the
`SurplusSpecTest` scenario, the user reads **$2,070** first, while the money they really have left
each month is **$1,500**. The $570 difference appears below it as "this already assumes you spend
less" — a correction to a number they should never have been shown first.

Leading with the shifted number reads as a promise. Leading with the real one reads as a starting
point, and turns every change after it into an improvement the user can see the value of.

## The figure

```
leftAsEntered = income − everything the user spends, exactly as entered
```

"Exactly as entered" means each line's `actual`, not its `counted` — fixed costs, capped categories
at what they really spend, going-out spending at what they really spend, tax set aside, and
separately-subtracted line items. Items that only *name part of* a category are skipped, by the same
rule `assumedReduction` already uses, or the same dollars are counted twice.

**Compute it in `SurplusCalculation`** and carry it on `SurplusBreakdown`. `assumedReduction`
already builds `observedSpending`; `leftAsEntered = income − observedSpending` is one line next to it.

**Do not derive it as `surplus − assumedReduction`.** It is equal only while going-out spending is
above the floor. A user who spends $150 going out against a $217.80 floor, and nothing above any baseline, has an `assumedReduction`
of zero (it is floored) and the subtraction would understate their real leftover by $67.80. Write
that as a test — it is the one a later refactor will break.

It may be **negative** and must not be clamped: someone spending more than they earn has to see that
first, not a positive plan figure.

`alreadySaving` is **part of** this figure, not subtracted from it — it is money they are not
spending. Show it as "of which you already move $X to savings" beneath the figure.

## What the user sees, in this order

1. **Where you stand today** — the first panel on the dashboard, above everything else.
   - Income, minus tax set aside, minus what you spend = **left each month**.
   - "Of which you already move $X to savings", when non-zero.
   - If any line was `assumed` (the user gave no figure and the local one was used), say so on this
     card and how many — it is then partly our estimate, and the card is the claim "this is from what
     you entered".
   - Negative: "You spend $X more than you earn each month", with the runway beside it.
2. **How to improve it** — the tips, each stated as what it adds per month, from what already exists:
   - each `surplus.reductions` entry (bring X down to the typical local figure: +$N),
   - each `cuts.suggested` entry (+$N),
   - each `hints` sentence (words only — a hint is never a figure and never enters a total),
   - `cuts.options` when still short.
   These close with the result: "Do all of this and you would have **$Y** a month for your goals",
   which is the plan's figure — so the shifted number arrives last, as the consequence of the tips.
3. Goals, left over, spending table, money in scope — as today.

The existing rule still holds: the plan figure is never shown without what it assumes beside it.
The new order satisfies it by construction, because the assumptions *are* the tips above it.

## Server shape

Add to `PlanView.Surplus` (or a sibling `Today` record — your call, say which in the PR):
`leftAsEntered`, `leftAsEnteredExplanation`, `estimatedLines` (count). Words come from the server,
like every other sentence on the plan. Amounts as two-decimal strings, as elsewhere.

**Snapshots are JSONB and append-only.** Every plan made before this ships has no such field and
never will. The client renders an old plan without the "today" panel — it must **not** recompute it
from the old snapshot's lines, because a snapshot is what the user was told, and they were not told
this.
