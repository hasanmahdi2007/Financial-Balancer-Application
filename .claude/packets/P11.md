# P11 — A plan belongs to a place

> Read `ARCHITECTURE.md` and `.claude/PACKET_RULES.md` first. P1–P8 and P10 have merged. This brief
> is split between the **server** (built by the P4 session, because no P6 session is running) and
> the **client** (P8). The contract between them is the section "The API", and neither side changes
> it without telling the other.

## What Hasan asked for

> When someone changes the place they live in, it should not show the same plan he was using for a
> different location. It should let him choose between old plans he had in this country, or make a
> new one.

## What happens today, and why

Every planning table is keyed by `user_id` alone: one location, one set of spending, one set of goals
and one line of history per person. `PUT /api/v1/profile` overwrites the location in place, so moving
from Beirut to New York re-prices the Beirut plan with New York's baselines. Beirut rent, Beirut
spending and Beirut's own figures all carry over, and the history mixes plans from both cities.

Two more things leak across a move for the same reason:

- **`user_category_override`** (P2) — "my rent is $600" typed in Beirut becomes the user's rent in
  New York.
- **`user_tax_override`** (P4) — a tax rate typed for Lebanon keeps applying in the US.
  `JdbcUserTaxRateLayer.rateFor` receives the country and ignores it.

## The model

A **plan** is a place plus the life the user leads there.

| Belongs to a plan | Belongs to the person |
|---|---|
| country and city | the balance and what share of it is in scope |
| lifestyle, least for enjoying life, whether income arrives taxed | bank connections and what the bank reads |
| monthly income | |
| spending, named items, own figures (`user_category_override`) | |
| goals and the finish-first choice | |
| snapshots, which means history too | |

**Why the balance is the person's.** The money in someone's account moves with them. Restoring a
two-year-old plan must not restore a two-year-old balance.

**Why the tax override is keyed by country, not by plan.** A rate is a fact about the user in a
country. Two plans in the same country should agree on it.

Exactly **one plan is active** at a time. Everything the app shows or changes today acts on the
active plan, so no existing screen changes except where the location is chosen.

## The flow

The user picks a new country or city (the location step, or "I've moved" from the menu):

- **They have no plan in that country.** A new plan is made there, and the setup questions run
  (lifestyle, income, spending).
- **They have one or more plans in that country.** They are shown a list. For each plan: the city, when
  it was last used, and what it said (left each month, number of goals). They either **pick one**,
  which becomes active with its inputs and history exactly as they were, or **start a new one**.
- **Starting a new plan** offers to **bring the current goals along**, ticked by default: a car you
  are saving for does not stop mattering because you moved. Nothing else is copied. Spending and own
  figures belong to the old place, and copying them would recreate the bug.

The old plan is never changed or deleted by a move. Nothing is ever deleted: coming back to a country
means picking up exactly where the user left off.

Same country, different city: the list shows plans from the whole country, as Hasan asked, each with
its city.

## The API

```
GET  /api/v1/plans                     every plan: id, country, city, lastUsedAt, active,
                                       summary {leftEachMonth, goals} or null if no plan was made yet
GET  /api/v1/plans?country=LB          the same, only that country (what the chooser shows)
POST /api/v1/plans                     {country, city | cityNotListed, bringGoals}
                                       -> the new plan, now active
PUT  /api/v1/plans/active              {planId} -> the plan, now active; then GET /plan returns its
                                       latest snapshot
```

`PUT /api/v1/profile` keeps working for everything except location. Changing the country or city of
a plan that has already produced a snapshot is refused with a problem detail
(`409`, `type: .../choose-a-plan`) whose body says, in words, to choose or start a plan for the new
place. A plan still in setup, with no snapshot yet, may change its location freely, because that is
correcting an answer, not moving.

All other endpoints act on the active plan and do not change shape.

## Server work

- **Migration V33** (P6's range): `planning_plan(user_id, id, country_code, city_slug,
  city_not_listed, created_at, last_used_at)` and `planning_active_plan(user_id PK, plan_id)`.
  `plan_id` is added to the per-plan tables (profile fields, income, spending, line items, goals,
  finish-first, snapshots) and to the keys that need it. Backfill: every existing user gets one plan
  from their current `planning_profile` location, and every existing row goes into that plan.
- **`plan_snapshot` is append-only by trigger.** The backfill disables the trigger inside the
  migration, sets `plan_id`, re-enables it and makes the column `NOT NULL`. The migration comment
  must say why this is the one sanctioned write, and that `body` is not touched.
- **V13** (P4's range): `user_tax_override` keyed by `(user_id, country_code)`. Existing rows take
  the country of the user's current profile. `JdbcUserTaxRateLayer` filters by country.
- **`user_category_override`** gains `plan_id`, backfilled the same way (P2's table, P6's migration
  range, so it goes in V33).
- Stores take a scope `(userId, planId)` in place of the bare `userId`. `PlanService` resolves the
  active plan once per request. **The user id stays the first key everywhere**, so no query can
  reach another user's plan by its id. Test that, as P6's authorization test does for snapshots.

## Client work (P8)

- The location step, and a new "I've moved" entry in the menu, call `GET /plans?country=` after the
  country is picked. With no plans, carry on as today (`POST /plans`, then setup). With plans, show
  the chooser: each plan's city, last used date and summary, a **"Use this plan"** button, and
  **"Start a new plan here"** with the "bring my goals" box ticked.
- A `409 choose-a-plan` from `PUT /profile` routes to the same chooser. It never reaches the user as
  an error message.
- The dashboard header names the active plan's place ("Your plan in Beirut"), so it is always clear
  which plan is on screen.
- History shows only the active plan's snapshots, because that is what the server returns.

## Done when

- Moving to a country with no plan: a new plan with no spending and no own figures carried over, and
  goals carried over only when `bringGoals` is true.
- Moving back: the old plan comes back with its inputs and history exactly as they were, and
  `GET /plan` returns its latest snapshot.
- A tax rate typed in Lebanon does not apply in the US. An own rent figure from Beirut does not
  apply in New York.
- User A cannot activate, list or read user B's plan by id.
- Every existing user's data migrates into exactly one plan, and their existing history is intact.
- Client: the chooser appears whenever the chosen country already has a plan, and the dashboard
  names the place.
- CI green on `verify -DskipITs=false` and the client suite.
