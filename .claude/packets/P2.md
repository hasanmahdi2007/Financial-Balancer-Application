## Do this first, before building anything on top

For five metros, compare `CEX_housing(quintile 3) × RPP_rents / 100` against Census ACS `B25064`
median gross rent. Within ~15% is defensible. A 2× gap means the category-to-component mapping is
wrong and **every downstream number in the product is poisoned** — silently, because nothing crashes.

**This is the highest-value check in the project and it takes an afternoon.** If it fails, stop and
report rather than proceeding.

## Build

1. **The Postgres schema** from `ARCHITECTURE.md` §8, as Flyway V1–V9: `country`, `metro_area`,
   `data_source`, `national_baseline`, `price_level`, `city_category_baseline`, `city_contribution`,
   and the user override tables. `@Enumerated(EnumType.STRING)` and `TEXT` columns always — an
   ordinal column plus a later enum reorder is silent data corruption, and ArchUnit enforces it.

2. **An offline Java ingestion tool, run by hand** for the initial seed — never at build time, never
   at boot. It writes committed CSVs into `resources/data/` and **commits the raw API responses too**,
   so no build and no test ever depends on BLS or BEA being reachable.

3. **A scheduled refresh job.** A Spring `@Scheduled` task re-pulls upstream, writes changed figures
   with their own `as_of` and confidence, and falls back to the committed seed when the network is
   down. Two constraints:
   - **Do not poll daily.** BEA RPP, BLS CEX and Census ACS publish **annually**. A daily job fetches
     identical bytes 364 days a year and burns the free quota for nothing. Make the interval
     configuration, default it to weekly, and make it a **no-op when the upstream `as_of` has not
     changed** — one cheap comparison, not a re-ingest.
   - **A refresh never overwrites a user's own figure.** `USER_PROVIDED` stays top of the chain
     regardless of what arrives.

4. **Two provider implementations, one contract.** `JpaCostOfLivingProvider`, and **keep**
   `ClasspathCostOfLivingProvider` reading the committed CSVs. Both must pass **the same shared
   abstract contract test**. That test costs almost nothing and is the proof the port is honest rather
   than decorative — and the classpath one keeps every pure domain test runnable with no database.

5. **`BaselineResolver` as an ordered list of layers**, not nested ifs:
   user override → `OFFICIAL` → `CONTRIBUTED` → `CROWDSOURCED` → country `ESTIMATED`.
   Adding a source must be appending one layer. The same chain resolves the tax rate.

6. **Staleness derived, not hardcoded.** `drift = annual_inflation × age_months / 12`; FRESH under
   5%, AGING to 15%, STALE beyond. The US at ~3%/yr stays fresh 20 months; Lebanon at 17.3% goes stale
   in ~10. Same code, opposite behaviour, one column. **Never auto-inflate a stored figure** — that
   fabricates precision. Offer the adjusted number as a pre-filled default the user confirms, at which
   point it becomes `USER_PROVIDED`.

7. **~20 US metros, not 382.** The marginal metro adds nothing to a demo. Include San Francisco and
   Wichita (the magnitude test needs them). Plus six Lebanese cities — Beirut, Tripoli, Sidon, Zahlé,
   Jounieh, Byblos — as `CROWDSOURCED` USD with an explicit `as_of`. Lebanon is de facto USD-priced
   since 2019, so no FX layer is needed; there is no RPP equivalent, so these carry absolute figures.

8. **The cascading catalogue endpoints** — countries, then that country's cities, each carrying
   confidence and `as_of`. A user-typed `city_label` is **display-only and never a lookup key**, which
   is what removes geocoding and fuzzy matching entirely: a typo can never almost-match the wrong
   metro. The manual form is **pre-filled** from the country `ESTIMATED` layer — eleven blank boxes is
   where users abandon signup.

9. **The contribution pipeline.** A user's figure is private to them on write, and becomes a city
   default only after passing validators **and** explicit approval. Bank corroboration is the
   validator that matters, because it is the only one that works with a single user: it checks a claim
   against that person's own transactions rather than against opinion. Quorum and MAD outlier
   rejection are designed but not built — say so in the README rather than implying a live
   crowdsourcing network exists.

JPA entities never escape `costofliving/persistence`.

## The quintile mismatch — measure it, then correct it

Two mismatches between what BLS measures and what this product asks for, and they pull **opposite**
ways, so the net error cannot be guessed:

1. **Income basis.** BLS quintiles are defined on *pre-tax household* income; the product collects
   *net personal* income. Comparing a net figure against pre-tax boundaries places many users a tier
   too low, which makes their baseline read **low**. Reference points: CEX 2024 average pre-tax income
   $104,207 against average expenditure $78,535.
2. **Household size.** CEX describes a consumer unit averaging **2.5 people**; this product is
   explicitly single-person. That makes the same baseline read **high**.

**Do not apply a correction factor before measuring one.** The ACS `B25064` comparison above is an
independent anchor for housing, so it sizes the real error rather than a theorised one. Run it first,
then correct.

When you do correct, both fixes are data, never constants in code:

- **Income basis:** `gross ≈ net / (1 − effectiveRate)`, reusing the per-country effective tax rate the
  resolver already provides. No new user input, and it self-adjusts for Lebanon where personal income
  tax is minimal and net is close to gross.
- **Household size:** a **per-category** factor, not one global number. Rent scales weakly with the
  number of people — a one-bedroom is not 40% of a three-bedroom — while groceries scale almost
  linearly. A single factor would fix food and break housing. As a starting point the OECD-modified
  equivalence scale (first adult 1.0, further adults 0.5, children 0.3) puts a 2.5-person unit near
  1.6 equivalent adults, implying roughly 0.6 for a single person — but treat that as a hypothesis for
  the ACS check to confirm or refute, not as an answer.

State whatever you conclude in the README. Visible assumptions read as rigour; hidden ones read as
naivety.
