`user_good`, which lacks the credit-card and loan accounts this packet needs. Dump the full
`/transactions/sync` and `/transactions/recurring/get` responses and **commit them as fixtures**

Build the PFC mapping from **what actually arrives**, not from the documentation's category list. A
gym membership may return `PERSONAL_CARE` rather than anything you would predict. Every test then runs
offline, which rule 9 requires.

## The three things that are easy to get silently wrong

1. **The sign convention is inverted from intuition.** Plaid: *"Positive values when money moves out
   of the account; negative values when money moves in."* A $700 salary deposit arrives as
   `amount = -700` and must be displayed as +$700. Getting this backwards inverts every number in the
   product, with no error anywhere.

2. **`LOAN_PAYMENTS_CREDIT_CARD_PAYMENT` is `TRANSFER_INTERNAL`, not spending.** Buy $300 of groceries
   on a card, then pay the card: counting both subtracts $600 for $300 of food. This is distinct from
   `DEBT_PAYMENT`, which is a real outflow to a *lender* rather than the settlement of spending
   already counted. `user_transactions_dynamic` has both a checking and a credit account, so this is
   directly exercisable rather than hypothetical.

3. **Unmapped categories land in `(SPEND, OTHER)`, increment a counter and are logged — never
   silently dropped.** Dropping spending makes the surplus look *better* than it is, which is the one
   direction of error the user must never be shown. Assert the unmapped count is zero across the whole
   fixture set.

## Also build

- **Classification on two axes.** `Classification(TransactionKind kind, SpendCategory category)`,
  category null unless `kind == SPEND`. Only `SPEND` becomes a category observation.
  `TRANSFER_INTERNAL` aggregates into `alreadySaving`, displayed but never subtracted.
  `TRANSFER_OUT_SAVINGS` and account transfers are internal; `INCOME_*` and `TRANSFER_IN_DEPOSIT` are
  income; `BANK_FEES_*` are fees.
- **Pair collapsing.** With both accounts linked, one internal transfer appears twice. Match opposite
  signs, equal magnitude, within ±3 days, same Plaid Item, and collapse to one record. An unmatched
  half still classifies from its PFC value alone.
- **Durable cursor.** Persist `next_cursor` so a restart resumes rather than re-importing.
- **Webhook idempotency.** Delivering the same webhook twice changes nothing. Handle
  `TRANSACTIONS_REMOVED` — a removed transaction disappears from the breakdown.
- **Pending transactions are not final.** Their amount can change before settling.
- **Async.** A sync must never sit on a user request path. `@Async` with a `TaskExecutor`; the API
  returns immediately.
- **Persist `merchant_entity_id`, `merchant_name` and location lat/lon from the first import.** P7
  needs them for observed merchant pricing, and a backfill later is work you can avoid now.
- **Request only the `transactions` product** in the link token. Money movement then is not declined —
  it is ungranted, because it would need `auth` or `transfer`. That is the difference between a
  promise and a structural guarantee, and it is the claim the trust article rests on.
- **Encrypt access tokens at rest.** They must never appear in logs or API responses.
