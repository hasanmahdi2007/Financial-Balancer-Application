## Build

The geo endpoints, profile, overrides, goals, `POST /plan`, `GET /plan`, `/plan/history`. RFC 9457
problem details, which are native in Boot 4.

`PlanAssembler` in `planning/application` is the **sole translator** between cost-of-living and
planning. It takes `ResolvedBaseline` objects and flattens them to bare `Money` before the math sees
them. **Confidence travels to the view, never into the formula** — the moment the math can see it,
someone writes `if (confidence == ESTIMATED)` inside the calculation and the branch sprawl begins.

Plans are **append-only snapshots**, so adding a goal never rewrites what the plan said before. That
is what lets `/plan/history` show exactly what changed when a goal was added.

## The gateway

Copy the gateway files out of `jobs-tracker-distributed-system`. **That repository is read-only —
never edit or commit to it**, even for something that looks improvable in passing. Make every
adaptation in the copies.

Keep its rate limiting unchanged. Extend auth with Supabase JWT validation against Supabase's JWKS,
and remove whatever the previous auth mechanism was where Supabase supersedes it, rather than leaving
it dead alongside. The gateway injects the user id; every `budget-core` query is scoped by it.

## The two tests worth more than the rest of the packet

1. **User A cannot read user B's plan.** Bank data is the most sensitive thing here, and one user
   reading another's is the failure that ends the product.
2. **`budget-core` is unreachable from outside the Compose network.** This is what justifies keeping
   the gateway at all: `budget-core` trusts the injected user-id header, so without network isolation
   that header is forgeable and the first test becomes unenforceable in production.
   `docker-compose.yml` publishes only the gateway's port, and the comment in that file is
   load-bearing.

## You own the composition, and it currently has a bug

**Added after P1 merged, at Hasan's instruction, because this is where the fix belongs and he did not
want it forgotten.** Nothing below is optional polish.

`SurplusCalculation` and `GreedyPriorityAllocator` are each correct on their own. **Joining them
naively produces a plan that lies.** Measured on the merged code, with the scenario in
`SurplusSpecTest`:

| | |
|---|---|
| Reported surplus | $2,070 |
| Cash actually left after real spending | $1,500 |
| Goals need | $2,250 |
| Cuts the plan suggests | **$180** |
| What the user must really change | **$750** |

The surplus is **not** money in hand. It is what the user would have *if* they cut to baseline and to
the floor — $570 here. Hand the allocator the surplus plus each category's **observed** spend as cut
candidates and it proposes $180, `residualGap` reads $0.00, and the user reasonably concludes the goal
is reachable. They follow the advice exactly and land $570 short.

Two things are required of you, and they are separate:

1. **Show both numbers wherever a plan reaches a person.** `SurplusBreakdown.assumedReduction()`
   already carries the $570, and `totalReductionNeeded(suggestedCuts)` already sums it with the
   allocator's cuts. Neither is optional in the response body. A plan that reports `tradeoffs`
   without `assumedReduction` beside it is the bug, not a simplification of it.

2. **Hand the allocator headroom, not observed spend.** A cut candidate must be what is *still*
   available to cut after the reduction the surplus already assumed — otherwise the allocator offers
   up money the formula has spent twice. For a `CAP_AT_BASELINE` category the surplus already charged
   only `min(actual, baseline)`, so there is no headroom left in it unless you intend to propose
   cutting below the local baseline, which is a different and louder thing to say. For
   `DISCRETIONARY` categories the headroom is what observed spending exceeds the floor, and it is a
   single pool across all of them, because the floor is one figure and not a per-category budget.

**Use each line's own `rigidity()`, never `category.defaultRigidity()`.** `CategoryLine` carries it
precisely so a gym the user marked `LOCKED` reaches the allocator locked. `CategoryLine.isCuttable()`
applies the same two conditions the allocator does; prefer it to rolling your own filter.

Write the composition test that fails today: goals short by some amount, follow only the suggested
cuts, and assert the user's real cash position reaches what the goals need. That test is worth more
than either of the two below.
