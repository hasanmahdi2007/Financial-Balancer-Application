## Build

The geo endpoints, profile, overrides, goals, `POST /plan`, `GET /plan`, `/plan/history`. RFC 9457
problem details, which are native in Boot 4.

**The catalogue endpoints already exist — extend them, do not rewrite them.** P2's brief required it
to build the cascading country/city/manual-form endpoints, so `costofliving/web/CatalogueController`
landed before this packet despite `*/web` being listed above as yours. That overlap is a mistake in
how these two briefs were written, not a rule P2 broke. The endpoints are covered by
`CatalogueEndpointIT`, including an assertion that no constant name reaches a payload. Adding
problem details and the remaining routes around them is the work; deleting and re-deriving them
would lose that coverage for nothing.

`PlanAssembler` in `planning/application` is the **sole translator** between cost-of-living and
planning. It takes `ResolvedBaseline` objects and flattens them to bare `Money` before the math sees
them. **Confidence travels to the view, never into the formula** — the moment the math can see it,
someone writes `if (confidence == ESTIMATED)` inside the calculation and the branch sprawl begins.

Plans are **append-only snapshots**, so adding a goal never rewrites what the plan said before. That
is what lets `/plan/history` show exactly what changed when a goal was added.

## Earmarking the considered balance — added after P4

> P4 built `ConsideredFunds` but could not build this half: it lives in `planning/application`,
> which you own. P4 shipped the other channel, the runway figure, and stopped at the boundary.
> Without this section a user with $50,000 in the bank is told a $20,000 car is infeasible.

There are **two quantities**, and conflating them is the trap. `monthlyIncome` is a rate and
`consideredBalance` is a stock — `ConsideredFunds` says so in its own javadoc. The surplus is what
funds goals each month; the balance is a pile that already exists and that no part of the surplus
formula touches.

`PlanAssembler` is where the stock reaches the plan, and it does so by **raising a goal's `saved`**:

```
remaining()           = target − saved
requiredMonthly(asOf) = remaining().spreadOver(monthsRemaining(asOf))
```

Crediting $20,000 to a $20,000 car goal makes `requiredMonthly` zero and frees the whole monthly
surplus for the next goal. No new concept — an existing lever, moved before the allocator runs.

**Three decisions, already made. Do not re-open them.**

1. **Order.** Earmark in descending priority. The user may additionally nominate **one goal to
   finish first**, and that goal takes the balance ahead of priority order. This affects earmarking
   only — the allocator keeps ranking priority-then-cheapest and keeps receiving one `Money`.

2. **Reversible at any time.** The user can pull money back out of scope whenever they like, by the
   same means they set it: exclude an account, flag a deposit, lower the share, or
   `ManualConsideredFunds.revisedTo(...)`. Re-running the plan afterwards must hand the money back
   — a user who cannot withdraw from a plan stops putting money in. Snapshots are append-only, so
   this is a new snapshot, never an edit to an old one.

3. **`saved` is derived from the balance, never typed independently.** This is the one that bites.
   If a goal could carry a hand-entered "already saved: $20,000" *and* receive a share of the
   considered balance containing those same dollars, the goal reads as funded twice. It is the third
   instance of a bug class this codebase already designs against — counting a savings transfer as
   spending, and taxing already-net income — except this one errs **optimistic**, which is worse:
   nothing looks wrong, the plan is simply a lie. Deriving `saved` from one source makes it
   impossible by construction rather than by a rule someone has to remember. **Write the test.**

**The hard constraint is unchanged.** `ConsideredFunds` must never be passed to the allocator.
`AllocationRequest` takes a single `Money` surplus, which is what makes `GreedyPriorityAllocator`'s
optimality argument hold — a stock divisible across goals is a second resource, and greedy is not
optimal for two. `ArchitectureTest.allocationEngineIsFrameworkFree` already forbids
`planning.domain` from depending on `..profile..`; if you find yourself wanting to relax it, the
design has gone wrong, not the rule.

Whatever is left unearmarked still drives `Runway.of(funds, monthlyDeficit)` for display, so the two
channels never disagree about the same dollars.

## The gateway

Copy the gateway files out of `jobs-tracker-distributed-system`. **That repository is read-only —
never edit or commit to it**, even for something that looks improvable in passing. Make every
adaptation in the copies.

Keep its rate limiting unchanged. Extend auth with Supabase JWT validation against Supabase's JWKS,
and remove whatever the previous auth mechanism was where Supabase supersedes it, rather than leaving
it dead alongside. The gateway injects the user id; every `budget-core` query is scoped by it.

Note that the jobs-tracker filter is a **reactive** `WebFilter` (`ServerWebExchange`, `Mono`), which
suits the gateway and does not port into `budget-core` — that module is on the servlet stack. Copy it
into `api-gateway/`, not into the core.

### The security chain already in `budget-core`

`com.hasan.budget.security.InternalServiceSecurityConfiguration` exists and **permits every request**.
It is not an oversight and it is not a stub to delete carelessly. The resource-server starter is on
the classpath, so with no configuration at all Spring Boot locks every route behind HTTP Basic and a
generated password — every endpoint in the service answers 401, including the health check Compose
depends on, and the symptom reads as a bug in whichever controller is being tested. P2 added the
chain so the service is runnable at all.

Its reasoning is written out in that file and comes down to this: re-validating the caller's token
here would check the same credential twice in the one place a second answer could only disagree with
the first. The real controls are network isolation and per-user query scoping, which are both yours.

**Your decision, not a leftover.** If you want defence in depth — validating the Supabase JWT here as
well, or requiring the injected user-id header so a misconfigured gateway fails loudly instead of
quietly serving anonymous traffic — that bean is where it goes and nothing else moves.
`CatalogueEndpointIT#theGatewayIsNotAskedToLogIn` guards the regression; update it rather than
deleting it if you tighten the policy.

## The two tests worth more than the rest of the packet

1. **User A cannot read user B's plan.** Bank data is the most sensitive thing here, and one user
   reading another's is the failure that ends the product.
2. **`budget-core` is unreachable from outside the Compose network.** This is what justifies keeping
   the gateway at all: `budget-core` trusts the injected user-id header, so without network isolation
   that header is forgeable and the first test becomes unenforceable in production.
   `docker-compose.yml` publishes only the gateway's port, and the comment in that file is
   load-bearing.

## Done when

The 6 authorization and plan-history behaviours are green, plus a committed `.http` file walking the
full happy path.

Earmarking postdates the specs, so write its tests too, to the same standard. At minimum: a goal
covered by the balance needs nothing monthly; a nominated goal takes the balance ahead of a
higher-priority one; taking money back out of scope returns it to the plan on the next run; and the
same dollars can never reach one goal twice.
